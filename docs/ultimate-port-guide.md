# Porting an Ultimate fighter: the framework

Every port so far found its bugs one test at a time: Hero took 75 fixes, Squirtle shipped five versions
with many of the same bugs again. This framework turns each of those bugs into either a default the
pipeline can't skip or a check the finished package must pass. The converters themselves are described
in docs/ultimate-fighter-port.md; this page is the procedure.

| tool | what |
|---|---|
| `tools/port_sources.py` | where Ultimate's files and the vanilla game are (`port_sources.json`, not committed) |
| `tools/ultimate_port.py` | the pipeline: `init`, `status`, `effects`, `stats`, `plan`, `run`, `check` |
| `fighters/NAME/port.json` | one fighter's settings (`init` fills it from Ultimate's files) |
| `reference/port_bases.json` | what each base fighter's own code does to a port built on it |
| `tools/ultimate_stats.py` | fighter_param stats from Ultimate's `fighter_param.prc`, by name |
| `tools/port_check.py` | the finished package against every bug class so far |
| `tools/vec_target.py` | Ultimate's "carry the hit fighter to a point" hits (set_vec_target_pos) as an MSC pull |
| `tools/ultimate_camera.py` | Ultimate's win cameras (camera/fighter/NAME/c00/j02win1-3) as Smash 4 result-scene camera motions (motion/camera/result/NAME/N) |
| `tools/result_param.py` | the loser panel's framing and win frames (`param/ui/result_param.bin`, by model name): `port` scales the base's entry to the fighter |
| `tools/costume_group_cave.py` | per-costume motion sets (`motion/body2` ...) for new kinds and the costume variables (exe_v46s) |

## What the user provides

Once (the shared files; every later port reuses them):
- Ultimate's `fighter/common/param` (fighter_param.prc, effect.prc), `effect/system/common/ef_common.eff`,
  the UI (`ui/replace/chara`), the sound folder;
- ParamLabels.csv (github.com/ultimate-research/param-labels);
- the smashline ACMD dumps (WuBoytH/SSBU-Dumped-Scripts, `lua2cpp_<name>`).

Per fighter: Ultimate's `fighter/<name>/` folder (model, motion, param/vl.prc), its
`effect/fighter/<name>/ef_<name>.eff`, and the trait (CLAUDE.md). Optional, for the specials: the
fighter's decompiled status code (OpenSmash-Ultimate's ssbu-recomp fighter tooling, run on the
user's own dump: Ultimate's speeds and logic for specials, which aren't in the ACMD or the params).

## The procedure

```
python3 tools/port_sources.py NAME                    # every input found?
python3 tools/ultimate_port.py init NAME --base BASE --kind 0x47 --ui-name "Name" --trait TRAIT
python3 tools/ultimate_port.py status NAME            # sources + the base's known traps
python3 tools/ultimate_port.py effects NAME           # his effects; Ultimate's common ones -> ef_common sets
python3 tools/ultimate_port.py plan NAME --out DIR    # every command, in order; '?' = an input missing
python3 tools/ultimate_port.py run NAME body model-c00 ... motions [motions-group2] low-models camera result-param effects sound scripts specials variants shapes stats portraits --out DIR
   (specials: the fighter's MSC / articles: fighters/NAME/NAME.c, weapons/, specials_acmd.json, its build script
    with port.json specials.build_args)
python3 tools/ultimate_port.py check NAME PKG [later packages ...]
```

The order matters: the models before the motions (the model step writes the base's material pacs: Hero
fix 74); the effects before the scripts (the scripts take the bank's ids); `variants` after the scripts and
specials (it scans the translated effect.bin, rebuilds the bank with the turned copies at the end, so no
other id moves, `--variants-last`, points the scripts at them and installs the bank); `shapes` after
anything that rewrites the vl file (the scripts / specials steps start from the base's).

**Rapid jabs (holding multi-hits)** are part of the `scripts` step: every Ultimate hit with
`ATTACK_SETOFF_KIND_OFF`, angle 361, no set knockback, KBG / BKB 30 or less and some damage (a rapid-jab loop) keeps
Ultimate's angle and gets `Hitbox_Hold(ID, 1)` after it (`tools/ultimate_acmd.py` HOLD_MODE 'hold'; the command:
`tools/hitbox_hold_cave.py`, exe_v46y_hold, Sm4shCommand v1.7.5), so the victim stays in the loop's reach as in Ultimate.
Ship the executable with the scripts. `port_check` S28 / X8 error when one is missing.

Sources (`port_sources.json`): `kind_folders.NAME` (add_fighter.py's folder: the base's sound banks under
his name), `soundlabeltable` (the user's current one), `s4_chr` (the user's ui/replace/chr) and
`templates.NAME` (add_fighter.py's portraits, a folder or ZIP:PREFIX), besides the Ultimate ones.

**The status code** (ssbu-recomp on the user's dump: `lua2cpp_<name>/c_*.c`, the NRO translated
instruction by instruction, no names, no data): `tools/recomp_hashes.py DUMP VL_PRC LABELS` lists which
function builds which hash40 (vl.prc labels, status / motion names). Most specials' numbers are in vl.prc
under ParamLabels' names (Squirtle's Withdraw: `param_special_s`); the NRO tells which status reads them.
Params it never builds (Withdraw's speed_x) are read in the executable's native code.

The slot itself (kind record in `tools/extra_kinds.json`, `add_fighter.py`, the executable caves) is
docs/kind-expansion.md; run every cave test with `--others` (Hero v4b).

**Texture ids** (`tools/fighter_texture_ids.py`): the game keeps loaded textures by id, so every model the
port adds (body costumes, low models, articles) numbers its textures in the fighter's own block:
0x40KK0000, KK = 0x80 + kind (Sephiroth 0x40C2...., Squirtle 0x40C6....), body cNN + 0x400 x NN (lNN the same
ids when it is a copy of cNN, else + 0x2000 + 0x400 x NN), article a + 0x4800 + 0x800 x a (+ 0x80 a costume with
its own pictures). `init` registers the fighter (`reference/port_bases.json` `_texture_ids`); a tool that writes
an article's `model.nut` takes `article_id(name, article)` (registering the article first). A copy of a base's
model with the base's pictures (Supamario's articles) keeps the base's ids. `port_check` T1 / T2 check it over
the whole install (other fighters' folders and the base's vanilla models too).

**Moves the base has no slot for.** Ultimate's rapid jab (Attack100Start / Attack100 / Attack100End) and angled
forward smashes (AttackS4Hi / Lw) go in common slots (0x53 - 0x55, 0x5E / 0x61) that some bases' motion tables leave
empty (ZSS: Byleth v1 had neither). Give the kind the animations (`tools/extra_kinds.json` "motions": the slot, the
anim name, Ultimate's motion_list flags: loop 0x2, move 0x4; `port.json` motions.add: `C00Attack100Start`,
`C00Attack100`, `C00Attack100End`, `C03AttackS4Hi`, `C03AttackS4Lw`), rebuild the executable's motion table
(`kind_expand_incremental.py`), and the scripts step translates them (`ultimate_acmd.py --slot-moves`, which
`ultimate_port.py` passes for every such move motions.add or the base's main.pac has). The common MSC does the rest
(Attack100 0x26 from the jab when the script turns ENABLE_100 on, the loop's continue check each hit; 0x5E / 0x61 from
the stick when the motion is there). `port_check` S11.

**Low models (LOD).** The off-screen magnifier and 8-player Smash draw `model/body/lNN`. Ultimate keeps a
lowest level of detail in each costume (`model/body/cNN/lod.xmb`: Byleth's `body_low` for `body_high`, his female
costumes' `hair_low`, `coatG_low`, `skirtG_low`); the `low-models` step builds lNN from it (`ultimate_fighter.py model
--lod-low`: each low mesh in its full mesh's slot, the full one left out; the same skeleton, checked byte for byte
against cNN's model.vbn / model.jtb) with cNN's `.nut` and face / eyelid packs, and copies cNN where Ultimate has none
(Steve, Squirtle). The low polygons take **cNN's own materials** (model.nud / metal.nud), each by its Ultimate material
label (`--materials-from-c`: body_low draws with body_high's labels), so lNN looks as the cNN installed and names only
its texture ids even when that cNN came from an older converter (Hero's: one skin ramp where today's build makes two);
where cNN's polygons aren't this build's, the low build's own materials with their pictures matched to cNN's ids. cNN in
OUT must be the installed one (copy the user's model/body/cNN in, as for Hero), or a rebuild: then `--own-ids` gives
lNN ids of its own (+ 0x2000 + 0x400 x NN), so no lNN id names another picture than the installed cNN's whatever that
cNN holds (Sephiroth's, Incineroar's in lowmodels_v1). `port_check` M6 (ERROR: no lNN), M10 (WARN: a copy where
Ultimate has its own).

**Win cameras.** Ultimate animates the result-screen camera per win pose (`camera/fighter/NAME/cNN/j02win1-3.nuanmb`,
camera-SSBU.zip: one `gya_camera` node and its field of view). So does Smash 4: its result scene's script
(`data/script/xscene_result.xtal`, script-smash4-vanilla.zip; Xtal bytecode, strings readable) loads
`motion/camera/result/<model name>/<n>/` for the winner and starts it on its camera (`start_motion`), falling back to
`motion/camera/result/default/1/` ("NOT FOUND CAMERA!"); the model name is the kind's folder name
(`get_fighter_model_name_from_fighter_kind`, 0x030ED508, kind_expand.py's table: `master` for 0x47). No executable
change: the `camera` step converts the cameras into the Final Smash camera form (`camera_motion.omo` / `.vbn`, Corrin's
one `gya_camera` bone) at `motion/camera/result/NAME/1-3/` (the data root, beside `fighter/`). `param/ui/result_param.bin`
holds the scene's other framing (team / MVP cameras, offsets). Byleth v3 is the first in-game test: the vanilla folders'
file names and node form, what `<n>` counts and the field of view (not in the motion) are still to confirm
(fighters/master/README.md "v3: win cameras"). `port_check` R1 (ERROR when Ultimate has them and the package doesn't).
(v2 wrote them to `fighter/NAME/camera/result/winN/`, which nothing reads.)

**The results screen, both halves are default steps.** The winner's side is the `camera` step above; the losers' side
is `result-param`: `param/ui/result_param.bin` frames every fighter's loser panel (eyex / eyey / eyez, tox / toy / toz),
holds the win frames (win1 - 5) and the MVP / team offsets, one entry a model name (the kind's folder name, the same
lookup: 0x0275DB24's kind-indexed table). A kind without an entry gets "missing" (all 0): the camera on its target,
the panel drawn empty (Byleth v1 - v16; Hero, Sephiroth, Incineroar, Steve, Squirtle and Supamario until
results_panels_v1). The step (`tools/result_param.py port`) copies the base's entry and fits it to the port:
- **framing** (eye / to and the MVP / team offsets) x the head's height in Ultimate's j02lose over the head's height in
  the base's J02Lose (the panel shows the lose pose: Bowser's hunched head is at 15.5, not his bind pose's 21.5); the
  same picture scaled about the floor. Without the base's result motions, the bind poses' head joints;
- **win1 - 3** the base's x the port's j02winN length / the base's J02WinN (vanilla's win N is 80 - 100 % of its
  motion: mean 0.93); without the base's motions, the length x 0.957 (the vanilla median); win4 / 5 0 unless the
  port has those motions; mvp_motion / team_motion / team_pos_scale_factor the base's;
- **built on the newest shipped file** (`port_sources.json` `"result_param"`, else the user's param/ui, else vanilla):
  the file replaces the whole table, so it has to carry every earlier port's entry; `--replace` rewrites the port's
  own entry in place on a re-run, every other entry byte for byte. Ship it in `INSTALL_TO_data_and_data_us_en/`.
Byleth's (v17, by hand: ZSS's framing, the same win rule) gives the same win frames through the step (125 / 169 /
156). `port_check` R1 (every win pose the package plays has its camera, ERROR) and R2 (the entry, a non-degenerate
camera, the other added kinds kept: ERROR; win frames past the port's motions: WARN).

**Costume groups (per-costume motion sets).** Some Ultimate fighters have a second motion set for some costumes
(Byleth: `motion/body/c01` is the female set, the same for c01 / c03 / c05 / c07; port_check M11 finds them: a costume
whose `a00wait1` differs from c00's). Smash 4 already does this for Bayonetta (costumes 4-7 but 2 play `motion/body2/`,
`bodyentry2/`, `bodyresult2/`, `bodyroutemap2/`); `tools/costume_group_cave.py` extends her mechanism to new kinds:
1. `tools/extra_kinds.json` record: `"motion_group2": [1, 3, 5, 7]` (the costumes of the second set), and rebuild the
   executable with `costume_group_cave.py` (its mask table; test `costume_group_test.py PATCHED ORIGINAL`);
2. `port.json` `motions.group2`: `{"costumes": ["c01", "c03", "c05", "c07"], "source": "c01"}`: the plan's model steps
   for those costumes merge bones by the source's motions, the `motions` step writes the first group's costumes' face /
   eyelid pacs only, and a new step `motions-group2` converts the source's motions into `motion/body2` ... (the same
   motion names: one motion table) with the group's own face / eyelid pacs; run `low-models` after (lNN copies them);
3. scripts: Ultimate's costume tests become in-game tests on the costume variables (`COSTUME` 0x0F000500,
   `COSTUME_PARITY` 0x0F000501, `MOTION_GROUP` 0x0F000502, read by Float_Var_Compare; same cave): the translator turns
   `FIGHTER_INSTANCE_WORK_ID_INT_COLOR % 2` and the sound scripts' `GET_VOICE_VARIATION == 0 ... 7` chains (even /
   odd timings) into COSTUME_PARITY tests (before v3 those sound scripts came out empty: every branch false);
4. memory: one more main.pac (Byleth's: 11 MB) per group in the match, only while a fighter of that group plays.
In battle every player has its own resource loader, so two players of one kind in different groups each load their
own set; the shared entry / result packs take kind x 9 + 1 (first group) / + 2 (second), as Bayonetta's do.

**Delivering:** `port_check.py` over the install as the user will have it: the full package plus every
fix package after it, in order. No ERROR goes out. A fix package that ships a file ships its partners
(`model.nud` with `model.nut`; a `game.bin` built on the current one, not vanilla's).

**Packages (every package, ports, fixes and tests alike): install roots named for what they are.** Files to install go
under `INSTALL_TO_data/` (its contents copied into the user's data folder: `INSTALL_TO_data/fighter/NAME/...`) and
`INSTALL_TO_code/` (into code/: the executable); test-only or optional files under a root saying so
(`TEST_ONLY_INSTALL_TO_data/`, `OPTIONAL_...`). Never wrap install files in a folder named like a fighter or a game
folder (`supamario/fighter/supamario/...`, `test/supamario/...`, `fighter/...` at a zip's top level next to other
things): the user copied a `supamario/` folder holding `fighter/supamario/script/...` INTO their fighter/supamario, the
files landed at fighter/supamario/fighter/supamario/... and the game kept loading the old ones (threads / time tests v1
and v2: two rounds lost). The README says, for each root, "copy the CONTENTS of X into your Y folder", with one full
example path.

## Stats

`tools/ultimate_stats.py` reads Ultimate's entry by name (ParamLabels.csv). Comparing the two games' tables
over the 51 fighters both have:
- the same in both games (so Ultimate's is the port's): jump x speeds, air-jump x speed (16, which the
  hand-made lists had at 1), double-jump height, air accel / speed / brakes (air brake y, 26, was left as
  the base's), gravity, fall / fast fall, weight, jump count, jab count;
- Ultimate's by design: walk / run (Ultimate is 1.05x / 1.1x on every fighter), dash, landing lag
  (~0.6x), jump squat 3;
- ground friction: Ultimate's x0.45, as every port (Smash 4's are 0.45-0.57 of Ultimate's);
- 264 rapid jab, 268 jump type (fly = Pit's multi-jump) from Ultimate's; 265 (side tilt count) never:
  the common combo repeats the first hit (Hero fix 16), the port writes its own loop.
- **Jump heights:** Smash 4's full / short hops equal Ultimate's for 48 / 47 of 51 fighters, so the data
  says x1: the default (user's call). Hero / Steve / Squirtle / Sephiroth were made at x0.82 / x0.9 and keep it
  in their port.json (`stats.jump_scale`).
- **Sizes** (`ultimate_stats.SIZE`, written by the stats step; fighter_sizes_v1). The size in game is fighter_param 44
  `scale` (the model module's scale at creation, `0x02E53E98`) x the model's own skeleton. The model step carries
  Ultimate's skeleton 1:1 (no scale in `ultimate_fighter.py`; every root bone, Ultimate's and the converted VBN's,
  at scale 1: Hero's HeadN 16.89, Sephiroth's 19.04, Incineroar's 16.76 in both), so the port's 44 is Ultimate's
  fighter_param.prc `scale`. Evidence that the two games' units are the same: of the 57 fighters both have (vanilla
  fighter_param.bin against fighter_param.prc), scale is equal for 41 and within 4 % for 13 (Samus 1.0 / 0.96, Zelda
  1.0 / 0.97, Lucina 0.92 / 0.95 ...: Ultimate's own retunes); the only outliers are the three Miis (1.0 / 1.15), whose
  models differ (Smash 4's Mii body is sized by fighter_param_etc's body table, its c00 head at 10.6); the world-unit
  stats (jump heights, gravity, camera_range_front) are the same numbers in both. The sizes that follow the fighter:
  45 shield (drawn on a model joint, MSC func_456: so x 44 in game too) = Ultimate's shield_radius x 0.88 (the median
  Smash 4 / Ultimate ratio, quartiles 0.84 - 0.95: APPROXIMATED; Ultimate changed shields per fighter), 48 tumble
  hitbox = 45 x 0.35 (56 of 57), 49 effect_scale and 185 freeze_size = Ultimate's effect_scale / ice_radius (equal
  for all 57). The vl file's hurtboxes, ECB and ledge boxes are in model units (x 44 in game: a new 44 moves the
  ledge reach with the body). Not changed (camera framing, not size): the camera boxes 117 - 126, height 97, item boxes.
  `python3 tools/ultimate_stats.py sizes PRC LABELS FP_IN FP_OUT [NAME ...]` re-applies the sizes alone to an
  existing fighter_param.bin (every other byte kept: to merge with another change to the same rows). `port_check` P4.
- **Per-port overrides** (fighter_params_v2), in `port.json` `stats`: `"size": {"scale": 1.0, ...}` (keys
  `ultimate_stats.SIZE_NAMES`: scale, shield_radius, tumble_attack_size, effect_scale, freeze_size) for a size the user
  wants other than Ultimate's (Hero keeps all five of his pre-fighter_sizes_v1 sizes, Robin's row's: 1.0 / 10.7 / 3.745 /
  1.05 / 8.6), and `"override": {"INDEX": value}` for a MAP word the port's moves can't take from Ultimate (Incineroar's
  263 jab count stays 2 while his jab is Bowser's Attack11 / Attack12: no Attack13 slot). The stats step
  (`ultimate_port.py stats` passes them as `--size` / `--set`), `ultimate_stats.py sizes` and `port_check` P2 / P4 all
  take them in place of Ultimate's (P2 / P4 print an INFO naming them; a row that differs from an override is a P4 ERROR).

## Checking effects offline: tools/fx_render.py

`python3 tools/fx_render.py NAME MOVE [MOVE ...] --build DIR --out OUT [--frames 0-40] [--every 4]`
draws a move's effects as Ultimate's files describe them (its .eff, its effect script) beside the converted
ones (the package's .ptcl / .efc, the translated effect.bin), a row per frame (side view of "top": forward
right, 5-unit grid). Stage 1: the particles' motion, shape, type, mesh, scale / alpha / colour over life
and their textures (first flipbook cell, a plain colour x texture combine: the converted side's colours
are approximate, its textures being made for our own pixel programs). Stage 2 (default, `--stage 1` for the
old drawing): each converted part drawn by its own pixel program (tools/latte_pixel.py: the latte-dis
disassembly run over every pixel of a triangle with numpy; checked against eft_pixel_test's reference on
1440 cases, and runs all 1336 unique vanilla programs) on its inputs (colour 0 / 1 = keys x colour scale,
alpha; a mesh's vertex colours; UVs x the slot's repeat), blended as the game does (ONE / INV_SRC_ALPHA on a
premultiplied template, else the emitter's blend). Not yet: the vertex programs (UV scroll / flipbooks are
the first cell), u_nwHdrRange taken as (1, 0, 0, 0), no bloom, the distortion pass not drawn. Both sides
apply a mesh's vertex colours (Ultimate's smash flash disc fades to its edge so).

It shows where the converter changed something (a dropped rotation, a lost texture, a wrong type). Where
both columns agree but the game doesn't, our reading of an Ultimate field is wrong in both (Squirtle v6:
the dash's droplets rise ~14 units in both columns, low behind his feet in Ultimate's footage; the down
