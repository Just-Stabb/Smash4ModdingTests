# Lock down sync before chasing rollback

A Smash 4 modpack's netcode can be upgraded, but in a fixed order. First, make every client provably identical and keep modded players away from vanilla ones. Second, tighten Smash 4's existing delay-based lockstep. Rollback comes last, as a long-term research project that only Cemu can run. Smash 4 online is **peer-to-peer lockstep over Nintendo's Pia library**. The server only brokers login, matchmaking and NAT traversal. Since Nintendo Network shut down on April 8, 2024, that server is Pretendo's open-source reimplementation. So any netcode change lives in `cross_f.rpx` and needs no server cooperation. The RPX is also the only layer that Cemu and real Wii U consoles share. That makes the most valuable realistic upgrade a **custom lockstep written in code caves on top of the game's own socket library**: it keeps Cemu-to-console crossplay, works with mods, and can remove most stutter and some frames of delay. Rollback is possible in principle only Slippi's way, by snapshotting a few megabytes of battle memory from a Cemu fork. But Cemu has no savestates and reads guest time from the host clock. The modpack's growing roster also keeps changing the state such snapshots would have to cover, and Slippi took seven months of full-time work on a binary that never changed. The urgent problems today are more ordinary. The modpack's Minecraft-stage caves pick the biome and the monsters from the clock and from local controller state, which guarantees online desyncs. Nothing stops a modded client from matchmaking into vanilla lobbies on Pretendo, whose rules allow gameplay mods only in private lobbies where everyone consents. **The recommended first step** has two parts. One is a determinism-and-identity pass: reseed those caves from the match's battle RNG and stamp a hash of the gameplay files into matchmaking. The other is a two-Cemu test match with a packet capture, which checks the pass and also answers the largest unknowns.

## Smash 4 online is client-side lockstep, so the server is not the bottleneck

Smash 4 runs matches peer to peer. Every console must have every player's input for a frame before it can simulate that frame. If an input is late, everyone stalls. The game never predicts inputs or undoes a frame: SmashWiki states that Smash "requires the exact position and action of every element of gameplay before it can do anything, and it is not possible to undo incorrect guesses" ([SmashWiki: Wi-Fi lag](https://www.ssbwiki.com/Wi-Fi_lag)). Inputs are the main payload, plus load-state messages. When one console loads something the others don't expect, such as a Final Smash after a Smash Ball, "after around 10 seconds, both ends acknowledge that a desynch has occurred, and all players are disconnected" ([SmashWiki: Online desynchronization](https://www.ssbwiki.com/Online_desynchronization)). This is the only desync detector anyone has documented, and nobody knows whether it also compares state checksums. Latency figures disagree. SmashWiki's frame-delay page says **seven frames of delay are always present in every mode, offline included** ([SmashWiki: Frame delay](https://www.ssbwiki.com/Frame_delay)). Its input-lag page instead gives 3 frames of input lag plus about one frame of display lag ([SmashWiki: Input lag](https://www.ssbwiki.com/Input_lag)). No public source measures the extra buffer that online play adds, or whether that buffer adapts to ping.

The transport is Nintendo's Pia, a full UDP mesh. One console is the host and handles join requests, and the mesh migrates the host if it leaves. NAT traversal goes through probe requests relayed by the game server, and the documented flow has no relay fallback ([NintendoClients wiki: PIA Overview](https://github.com/kinnay/NintendoClients/wiki/PIA-Overview)). Pia offers Unreliable, Reliable, Clone and **Sync** data protocols, plus a Sync Clock protocol in which the host keeps a mesh-wide clock from median round-trip times ([Sync Protocol](https://github.com/kinnay/NintendoClients/wiki/Sync-Protocol); [Sync Clock Protocol](https://github.com/kinnay/NintendoClients/wiki/Sync-Clock-Protocol)). The session key comes from the game server during matchmaking. Up to Pia 5.6, packets were AES-ECB encrypted with an HMAC-MD5 ([Pia Protocol](https://github.com/kinnay/NintendoClients/wiki/Pia-Protocol)). Which Pia version Smash 4 links, and which protocol carries its per-frame inputs, are not documented anywhere.

Official online play ended with the Nintendo Network shutdown at **00:00 UTC on April 9, 2024** ([Wikipedia: Nintendo Network](https://en.wikipedia.org/wiki/Nintendo_Network)). Pretendo revived it with a dedicated Go server that implements NEX 3.6 with access key `2869ba38`. The server includes matchmaking, NAT traversal, an SSB4-specific DataStore for profiles, the Global Smash Power chart and replays, and stubbed referee and ranking protocols ([super-smash-bros-wiiu: secure.go](https://raw.githubusercontent.com/PretendoNetwork/super-smash-bros-wiiu/master/nex/secure.go); [register_secure_server_nex_protocols.go](https://raw.githubusercontent.com/PretendoNetwork/super-smash-bros-wiiu/master/nex/register_secure_server_nex_protocols.go)). Smash went public on Wii U and 3DS in a Pretendo post that dates to **April 11, 2025** ([Pretendo on X](https://x.com/PretendoNetwork/status/1910780460981968955)). Secondary summaries say January 2025, but the primary post is more reliable. For Fun, For Glory and With Friends work. Spectate, Conquest and the Miiverse stage do not, and the server reportedly hits a room-creation limit ([Unofficial Pretendo wiki](https://wiki.pretendo.zip/game-support-status)). The player base is small: a July 2026 forum thread says "there is simply not a lot of people playing it" ([Pretendo forum](https://forum.pretendo.network/t/i-am-trying-to-play-smash-bros-on-my-wii-u/29411)).

Cemu runs the console's own online stack. It needs a dumped `otp.bin`, `seeprom.bin`, certificates and a PNID-linked account, and its network-service menu offers Offline, Nintendo, Pretendo and **Custom**. Custom reads URL overrides from `network_services.xml` ([Cemu GeneralSettings2.cpp](https://raw.githubusercontent.com/cemu-project/Cemu/main/src/gui/wxgui/GeneralSettings2.cpp); [NetworkSettings.cpp](https://raw.githubusercontent.com/cemu-project/Cemu/main/src/config/NetworkSettings.cpp)). Consoles reach Pretendo through the Aroma plugin Inkay, and the same account works on both platforms, so Cemu and Wii U players already meet in ordinary Smash 4 lobbies ([EmuDesk 2026 guide](https://emudesk.com/issues/cemu-pretendo-network-wii-u-online-2026)). That guide is a low-authority source and mentions "some occasional desyncs" without a cause. **Smash 4 on Wii U has no LAN or local-wireless mode**, so there is nothing to tunnel ([SmashWiki: Local Wireless](https://ssbwiki.com/Local_Wireless)). The practical result is that the netcode sits entirely inside `cross_f.rpx`. Pretendo only puts peers in touch, so a modpack can change how frames are exchanged without asking anyone. The constraint is that it must keep using, or carefully replace, the NEX matchmaking flow that hands out Pia session keys.

## Community precedents split into "tune the delay" and "rebuild around one frozen binary"

Every community that improved a commercial fighting game's netcode without source access followed one of two patterns. The Ultimate scene tuned the stock netcode. HDR's November 2022 beta let "online input latency... be individually selected and tuned by both parties, akin to Dolphin input buffer" ([HDR on X](https://x.com/hewdrawremix/status/1597744718778990593)). The standalone `latency-slider-de` plugin does the same for any Ultimate online mode ([GitHub: Naxdy/latency-slider-de](https://github.com/Naxdy/latency-slider-de)). There is a catch that a Smash 4 version must avoid. Ultimate does not synchronise delay between players, so the slider value "replaces the 4f provided by ultimate" for one side only, and a modded player can play with fewer frames of delay than their opponent ([blu-dev: Latency Slider Explanation](https://gist.github.com/blu-dev/e227d57a9e745fd8768bc3d41c8ea6b4)). No Ultimate mod has replaced the netcode itself.

Project Slippi is the other pattern, and it shows what rollback really costs. Melee's rollback is a hybrid. ASM patches in the game signal frame boundaries to the Ishiiruka Dolphin fork through a fake EXI device. The emulator then copies only selected regions of guest RAM: data/BSS, one unknown region and the main heap, about **7.74 MiB**. Sound blocks and the XFB are excluded, and CPU registers and most hardware state are skipped ([Ishiiruka SlippiSavestate.cpp](https://raw.githubusercontent.com/project-slippi/Ishiiruka/slippi/Source/Core/Core/Slippi/SlippiSavestate.cpp); [slippi-wiki](https://github.com/project-slippi/slippi-wiki/blob/master/GETTING_STARTED.md)). It shipped on June 22, 2020, after about **seven months of full-time work** on top of years of earlier replay infrastructure ([GBAtemp](https://gbatemp.net/threads/project-slippi-is-a-build-of-dolphin-that-adds-rollback-netcode-to-super-smash-bros-melee-netplay.568152/page-2)). It works because it targets one binary, NTSC 1.02, whose memory the community had mapped for years. The launcher rejects every other ISO hash, including popular mods such as 20XX ([slippi-launcher verify_iso.ts](https://github.com/project-slippi/slippi-launcher/blob/main/src/main/verify_iso.ts)). Commercial retrofits confirm the cost. Rollback in Mortal Kombat X took "approximately eight man-years", Rivals of Aether's studio abandoned a retrofit as "too costly", and Skullgirls added GGPO in about two weeks only because it did so early, in its own engine ([Ars Technica](https://arstechnica.com/gaming/2019/10/explaining-how-fighting-games-use-delay-based-and-rollback-netcode/)).

Dolphin netplay, used by Project+, sits between the two. It is plain delay-based lockstep with an adjustable pad buffer. It only works when everyone runs the same emulator build, ISO, Gecko codes and SD-card contents, and it refuses mismatched Dolphin versions outright ([Dolphin NetPlayServer.cpp](https://github.com/dolphin-emu/dolphin/blob/master/Source/Core/Core/NetPlayServer.cpp); [SmashLadder desync guide](https://www.smashladder.com/guides/view/26pv/desync-troubleshooting-guide)). Emulator-wide rollback has succeeded only where whole-machine snapshots are cheap. In May 2026 an N64 fork, RMG-K, added rollback through GekkoNet and cut one Spain–Australia session from 9 frames of delay to 4 ([Time Extension](https://www.timeextension.com/news/2026/05/it-was-honestly-not-that-hard-this-nintendo-64-emulator-lets-you-play-online-with-rollback-netcode)). Fightcade's FBNeo does the same for arcade boards ([Flathub: Fightcade](https://flathub.org/en/apps/com.fightcade.Fightcade)). No Wii U or Switch emulator has netplay or rollback, and no Smash 4 netplay project turned up in searches.

| Precedent | What changed | Platform reach | Lesson for the modpack |
|---|---|---|---|
| HDR / latency-slider (Ultimate) | Input delay of stock netcode | Console and emulator | Cheapest win, but delay must be negotiated symmetrically |
| Dolphin netplay / Project+ | Emulator-level lockstep, hash checks | Emulator only | Identity checks matter more than the netcode model |
| Slippi (Melee) | Game-aware partial-RAM rollback in a Dolphin fork | Emulator only | Feasible on a frozen, fully mapped binary; ~7 months full-time |
| RMG-K, Fightcade | Whole-machine savestate rollback | Emulator only | Works only where full snapshots cost little |
| MKX, GG XX AC+R | Publisher rollback retrofits with source | Native | 8 programmer-years without a rollback-ready engine |

## Rollback in Smash 4 collides with memory size, host time and a moving target

GGPO states the requirements plainly. The simulation must be fully deterministic, and the engine must "load, save, and execute a single simulation frame without rendering", with the RNG state included in the saved state and effects and sounds deferred until the rollback ends ([GGPO Developer Guide](https://github.com/pond3r/ggpo/blob/master/doc/DeveloperGuide.md)). Smash 4 meets the first condition on any one build. Replays store only each human's inputs, the match seed and the rules. CPU players are re-simulated from the seed and "react to everything the exact same way" ([SmashWiki: Replay](https://www.ssbwiki.com/Replay)). Smash 4 fails the second condition, and each of the three possible places to add rollback fails it in its own way.

**Whole-machine rollback inside Cemu is infeasible.** Cemu has no savestate code at all. Issue #898, still open in 2026, has the lead developer listing what one would need: every PPC thread context, a full RAM dump, a serializer for every CafeOS and IOSU module, VRAM-only textures and GPU caches. Netplay is never mentioned ([Cemu issue #898](https://github.com/cemu-project/Cemu/issues/898)). The guest map reserves **1 GiB of MEM2** plus 32 MiB of MEM1 and a 64 MiB foreground bucket ([Cemu MMU.cpp](https://github.com/cemu-project/Cemu/blob/main/src/Cafe/HW/MMU/MMU.cpp)). At an assumed 10 GB/s memcpy, saving that once would take about 100 ms, six times a whole frame (estimate). Worse for determinism, guest time comes from the host CPU's `rdtsc`, scaled to the Espresso clock. `OSGetTime`, `OSGetTick` and `mftb` therefore return different values on two machines, and on the same machine during a re-simulation ([Cemu PPCTimer.cpp](https://github.com/cemu-project/Cemu/blob/main/src/Cafe/HW/Espresso/PPCTimer.cpp); [coreinit_Time.cpp](https://github.com/cemu-project/Cemu/blob/main/src/Cafe/OS/libs/coreinit/coreinit_Time.cpp)). Dolphin, by contrast, emulates a fake timebase and compares it between peers every 60 frames to detect desyncs ([Dolphin NetPlayClient.cpp](https://github.com/dolphin-emu/dolphin/blob/master/Source/Core/Core/NetPlayClient.cpp)). One fact helps. Cemu's bundled profiles pin Smash 4 to **Singlecore-Recompiler** in all three regions, so all three guest cores interleave on one host thread with cycle-counted time slices. The only scheduling jitter is a fixed-seed LCG ([game profile 0005000010144f00.ini](https://github.com/cemu-project/Cemu/blob/main/bin/gameProfiles/default/0005000010144f00.ini); [coreinit_Thread.cpp](https://github.com/cemu-project/Cemu/blob/main/src/Cafe/OS/libs/coreinit/coreinit_Thread.cpp)).

**Game-aware rollback in a Cemu fork is plausible but unmeasured.** The Slippi template carries over to Smash 4. RPX caves would add a frame-boundary marker at the top of the battle update, a "resimulating" flag that suppresses effect, sound and render submission, and a dedicated fixed-address arena for every battle allocation, made by hooking `operator new` (`0x03374578`) and heap alloc (`0x03374530`) during a battle scene. Cemu would memcpy that arena, plus `.data/.bss`, into a ring buffer each frame. Because the addresses never move, the raw pointers inside the battle objects stay valid after a restore. The state to capture is large but bounded ([docs/native-notes.md](/home/user/Smash4ModdingTests/docs/native-notes.md)). It includes every `BattleObject` and the modules behind its module accessor, ACMD interpreter states (0x38 bytes each, with separately allocated nested CALL states) and the global 32-thread ACMD pool, MSC VM state, the 16-word battle RNG at `0x105759C0`, stage objects with moving collision, item spawners, and the pad manager's per-slot histories at `0x1057581C`, which feed the 10-frame input buffer and smash-input detection ([docs/acmd-extra-commands.md](/home/user/Smash4ModdingTests/docs/acmd-extra-commands.md); [docs/minecraft-world.md](/home/user/Smash4ModdingTests/docs/minecraft-world.md)). Four things remain unknown: the battle's real memory footprint, whether battle logic reads the clock or GPU state anywhere, how effects and sound hold references to battle objects, and whether one host thread can run Smash 4 three to five times per 16.7 ms. Mid-match loads such as Final Smashes and items would also have to be preloaded or pinned. Even when it works, this route covers **Cemu players only** and splits a player base that is already small.

**In-RPX rollback on a real Wii U is the hardest route.** The Espresso runs at 1.24 GHz on 12.8 GB/s of shared DDR3 ([WiiUBrew: Hardware](https://wiiubrew.org/wiki/Hardware)). Copying even 16 MiB per frame would cost a few milliseconds before any re-simulation (estimate), and Smash 4's CPU headroom has never been measured. Cross-platform rollback also needs Cemu's recompiled floating point to match real hardware bit for bit. Mixed Cemu–console lobbies already working on Pretendo is weak evidence that it does.

**The growing roster turns rollback into a maintenance problem as well as an engineering one.** Slippi's region map was tuned once for a binary that never changes. Every new fighter, weapon or stage in this modpack adds new allocations, new ACMD effect and sound calls that must be muted during re-simulation, and new chances for state to live outside the arena. Each release would need a GGPO-style sync test, a forced one-frame rollback every frame with state checksums compared ([GGPO Developer Guide](https://github.com/pond3r/ggpo/blob/master/doc/DeveloperGuide.md)), before it could go online. Rollback is still worth having at the right moment. That moment is after the roster stabilises, not while it is still growing.

**Improved lockstep is the realistic target.** Remote players' inputs already arrive in the pad manager's network slots 17–24 as ordinary pad wrappers ([docs/minecraft-world.md](/home/user/Smash4ModdingTests/docs/minecraft-world.md)). A replacement can leave Pia's mesh alone and change only how those slots are filled. Inputs are tagged with an explicit frame number and carried over a UDP socket opened through the game's `nsysnet` imports, which Cemu already implements on host sockets ([Cemu nsysnet.cpp](https://github.com/cemu-project/Cemu/blob/main/src/Cafe/OS/libs/nsysnet/nsysnet.cpp)). Because the code lives in the RPX, Cemu needs no changes and crossplay survives. Console builds just apply the documented address offsets (+`0x0A000000` code, +`0x00503000` data) or run as a WUPS plugin, the mechanism Inkay uses to override Pia ports for Mario Kart 8, Splatoon and Minecraft ([PretendoNetwork/Inkay](https://github.com/PretendoNetwork/Inkay); [WiiUPluginSystem example](https://github.com/wiiu-env/WiiUPluginSystem/blob/main/plugins/example_plugin_cpp/src/main.cpp)). The available improvements, roughly by expected gain, are:

- a fixed, symmetric delay derived from measured RTT instead of whatever the stock buffer does;
- sending the last several frames' inputs in each packet, so one lost packet doesn't cause a stall;
- a time-sync step that briefly pauses the peer that is ahead, which Ars Technica describes as necessary under any netcode ([Ars Technica](https://arstechnica.com/gaming/2019/10/explaining-how-fighting-games-use-delay-based-and-rollback-netcode/));
- port forwarding or a relay when NAT traversal fails.

The ceiling is hard. Lockstep cannot run with less delay than the one-way latency in frames without stalling, so at regional pings the gain is perhaps **1–4 frames** plus the removal of most stutter (estimate). The stock online buffer has never been measured, so even that range is a guess. A Dolphin-style netplay inside Cemu, which syncs `VPADRead`/`KPADRead` and adds a virtual timebase, would avoid reverse-engineering Smash 4's netcode and would work in every mode. It gives no latency advantage over RPX lockstep, though, and it locks out consoles.

| Route | Platforms | Latency gain | Main blocker | Effort | Risk |
|---|---|---|---|---|---|
| Symmetric delay patch to stock netcode | Both | 0–3 frames (estimate) | Finding the buffer constant | Low | Low |
| Custom lockstep in RPX caves over `nsysnet` | Both, crossplay kept | 1–4 frames, far less stutter (estimate) | RE of the input path and match setup | Medium–high | Medium |
| Dolphin-style netplay in a Cemu fork | Cemu only | Same as lockstep | Virtual timebase, hidden host-time reads | High | Medium–high |
| Game-aware rollback in a Cemu fork | Cemu only | Large at high ping | Battle arena, resim suppression, CPU headroom | Very high | High |
| Rollback inside the RPX on console | Both in theory | Large | Espresso headroom, snapshot bandwidth, FP parity | Extreme | Very high |

## Mods desync any lockstep unless every simulated byte matches

Under lockstep, and under rollback too, every file and every code path that feeds the simulation must be bit-identical on all peers. Only presentation may differ. SmashWiki's rule of thumb fits: textures carry "very little risk", model hacks are "very likely" to desync, and "moveset and physics hacks are nearly guaranteed to desynch", while "players using identical hacks generally do not cause a desynch" ([SmashWiki: Online desynchronization](https://www.ssbwiki.com/Online_desynchronization)). For this modpack, the files that must match exactly are fighter_param, ACMD game scripts, MSC `.mscsb` files, any motion data whose bones carry hitboxes or hurtboxes, stage LVD collision and logic, item tables, the new kind slots `0x41`–`0x43`, and every code cave that runs during a match, from roll-off and reverse tilts to Stick Smash handling. Music, textures, UI art and Cemu resolution packs can differ freely. A vanilla peer cannot represent the new kinds or stage IDs at all, which is why community reports describe a replacement fighter showing up as the original character on the opponent's screen and then desyncing ([GBAtemp: Sm4shExplorer thread](https://gbatemp.net/threads/sm4shexplorer-wii-u-only-for-now.416118/)).

The modpack already contains two certain desync sources. The Minecraft stage's biome cave ORs every controller's held buttons at stage-setting build time and, with no L held, picks "random (the time base)". The monster cave rolls three spawns per cycle "on the clock RNG", which is instance 1 of the game's xorshift generator, seeded from the clock rather than from the per-match seed used for replays and online. The design notes already flag "online / replays (a clock pick isn't synced)" ([docs/minecraft-world.md](/home/user/Smash4ModdingTests/docs/minecraft-world.md)). Online, each console sees only its own physical controllers at setting-build time and its own clock, so peers will load different biome folders and spawn different monsters. That is a gameplay desync, and with a different stage folder probably also a load mismatch that triggers the 10-second disconnect. Both caves must draw from battle RNG instance 0, or from a value derived from the match seed or the synced match settings, and must make the same number of draws on every peer. The same rule applies to any future "random per match" feature.

Isolation from vanilla players is both a technical need and a policy requirement. Pretendo bans cheating that disrupts non-consenting players, first with account bans and then with console bans. It permits hacks only "in private lobbies if everybody consents" ([Pretendo Code of Conduct](https://forum.pretendo.network/t/pretendo-network-online-services-code-of-conduct/30557); [Pretendo forum FAQ](https://forum.pretendo.network/t/frequently-asked-questions-regarding-pretendo-network-and-pretendo-forums/4339)). Smash 4 itself never checked file integrity. Its only gate was requiring the latest patch ([SmashWiki: Online play](https://www.ssbwiki.com/Online_play)). Three levers are available, and they stack:

1. **Matchmaking tag, no server changes.** Pretendo's common matchmaking filters sessions by exact or ranged `game_mode`, `attribs[i]` (index 1 is reserved for the selection method and ignored), system type and participant counts ([nex-protocols-common-go: find_matchmake_session_by_search_criteria.go](https://github.com/PretendoNetwork/nex-protocols-common-go/blob/main/matchmake-extension/database/find_matchmake_session_by_search_criteria.go)). An RPX patch that writes a truncated hash of the gameplay files into a field vanilla always constrains splits the modpack into its own pool, one per version. NEX 3.6 has no `codeword` field ([NintendoClients wiki: Match Making Types](https://github.com/kinnay/NintendoClients/wiki/Match-Making-Types)). Inkay already does the same kind of thing for Mario Kart 8 modpacks "by simulating extra DLC" ([Inkay](https://github.com/PretendoNetwork/Inkay)). One caveat: if vanilla leaves that field unconstrained, vanilla searches still match modded sessions, so the field must be chosen from captured traffic.
2. **Peer-to-peer handshake guard.** A cave exchanges the same hash in the first reliable Pia message after joining, and leaves on a mismatch. This also covers With Friends joins, which skip search criteria.
3. **Separate server.** A self-hosted fork of Pretendo's AGPL Smash server, with Cemu's Custom service and an Inkay-style redirect on consoles, gives full control at the cost of running infrastructure ([super-smash-bros-wiiu README](https://raw.githubusercontent.com/PretendoNetwork/super-smash-bros-wiiu/master/README.md)).

Keeping everyone on one build follows the pattern that every successful community converged on. Dolphin's netplay `SyncIdentifier` hashes everything that affects sync, including mod-patch XML and options, and reports `DifferentHash` before a match starts ([Dolphin SyncIdentifier.h](https://github.com/dolphin-emu/dolphin/blob/master/Source/Core/Core/SyncIdentifier.h)). Slippi's launcher whitelists known-good hashes. HDR ships one versioned package, disables Quickplay outright, and keeps stable and nightly channels apart ([HDR-Releases](https://github.com/HDR-Development/HDR-Releases); [blu-dev gist](https://gist.github.com/blu-dev/e227d57a9e745fd8768bc3d41c8ea6b4)). For a growing pack, the manifest should list SHA-256 hashes of the RPX patch list and every gameplay file, and leave out cosmetic files so skins and music stay optional. The installer should verify it. The short hash should appear in-game and go into the matchmaking tag. With a roster that changes every release, "mostly the same version" means "different", so the check must be exact.

## Ranked paths: fix determinism and identity, then measure, then rebuild lockstep

The paths below are ranked by effort and risk together, cheapest first. Each depends on the ones before it.

| Rank | Path | Effort | Risk | Payoff |
|---|---|---|---|---|
| 1 | Determinism hygiene: move clock/time-base and local-controller picks to the match seed or synced settings; ban host-time reads in caves | Low | Low | Removes known modpack-only desyncs; required by every later path |
| 2 | Identity and isolation: gameplay manifest hash, matchmaking tag, P2P handshake guard, verifying installer, friends/private-only play | Low–medium | Low | Keeps modded players out of vanilla lobbies, in line with Pretendo rules; stops version-skew desyncs |
| 3 | Measure and tune stock netcode: capture traffic, find the online buffer and input channel, apply a symmetric delay patch and an optional port override | Medium | Low–medium | First latency gain on both platforms with no new protocol |
| 4 | Modpack matchmaking server (Pretendo fork) | Medium | Medium (ops, policy) | Full control of pools and versions; needed only if Pretendo's room limits or policies get in the way |
| 5 | Custom frame-numbered lockstep in RPX caves over `nsysnet`, filling pad slots 17–24 | Medium–high | Medium | Less stutter, packet-loss tolerance, time sync; keeps Cemu↔console crossplay |
| 6 | Cemu-fork netplay with a virtual timebase | High | Medium–high | Direct-IP play in any mode, Cemu only |
| 7 | Slippi-style game-aware rollback in a Cemu fork | Very high | High | Real rollback at high ping, Cemu only; worth considering only once the roster stops changing |
| 8 | Rollback inside the RPX on console | Extreme | Very high | Not recommended without measurements showing Espresso headroom |

**Recommended first step:** do ranks 1 and 2 together as one build, then test it. Change the biome cave and the monster cave to derive from battle RNG instance 0, or from synced match settings, instead of the time base and local controllers. Stamp a truncated gameplay-manifest hash into a matchmaking attribute. Then play two Cemu instances of that build against each other in a With Friends match on Pretendo, with a packet capture running. The match checks that the Minecraft stage stays in sync. The capture shows which `game_mode` and `attribs` fields Smash 4 fills and searches on, which tells you where the tag must go. Pretendo's handler logs the gathering it receives, so a self-hosted server shows the same thing. The capture also shows how often packets go out, which hints at how inputs are carried. All of this costs days, not months, and every later path depends on it.

Several questions need measurement or reverse engineering before ranks 3–8 can be scoped:

| Open question | Why it matters | How to answer it |
|---|---|---|
| Which Pia version Smash 4 links, and whether inputs go over Sync, Unreliable or Reliable | Determines the hook point and the packet format for any lockstep change | Search `cross_f.rpx` for Pia version strings and symbols; trace sends from the network pad slots |
| Size of the online input buffer, and whether it adapts to RTT | Sets the realistic gain of a delay patch (rank 3) | Frame-step a two-Cemu match with injected latency; find the buffer constant in the RPX |
| How the game detects desyncs (load acknowledgements only, or state checksums) | Decides whether a custom lockstep must add its own checksum | Trace what happens after a forced mismatch; look for hashing near the Pia receive path |
| Which matchmaking fields vanilla always constrains | Decides whether the tag actually isolates the pools | Packet capture against Pretendo or a self-hosted server |
| Where the match seed for RNG instance 0 is set, and where the per-frame battle update starts | Needed for seed agreement in lockstep and for the frame-boundary hook in rollback | RE of the scene system (`0x033B9F18`, launcher `0x02C881D4`) into the battle step |
| Whether battle logic reads `OSGetTime`/`mftb` or GPU state | Any such read breaks determinism in Cemu netplay or rollback | Breakpoint those calls in Cemu during a match |
| Size and layout of the battle heap | Decides whether a snapshot is ~8 MiB or far larger | Dump allocator traffic from the `0x03374530` hooks during a match |
| Host time per guest frame for Smash 4 in Cemu, and Espresso headroom on console | Sets how many frames a rollback could re-simulate | Profile both with a 2-player match on a large stage |
| Cemu↔console floating-point parity | Decides whether crossplay can survive any lockstep | Run long mixed-platform matches with periodic RNG and position hashes |

## Conclusion

The bottleneck is less the netcode model than the modpack's discipline about determinism and identity. Lockstep fails the same way rollback does when two peers' simulations differ. Rollback only hides latency; it does nothing for a pack whose stage rolls monsters from each console's own clock or whose versions drift apart between friends. A growing roster also points toward lockstep, because rollback's state map has to be revalidated with every new fighter, while frame-numbered lockstep in the RPX does not care what the frames contain. It only needs every peer's simulation to be identical.

The deeper structural point is that `cross_f.rpx` is the one artifact Cemu and real Wii U consoles share. Any upgrade built there keeps crossplay and stays independent of Pretendo, and any upgrade built in an emulator fork divides a small community in two. That makes RPX-side lockstep the sound long-term investment. A Cemu-only rollback fork is worth revisiting only after the roster settles, the battle heap has been measured, and the community is large enough to absorb a platform split.
